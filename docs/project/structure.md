# Structure

Canonical placement rules for MediaStack. Consumed by contributors and review tooling.
For deep architectural narrative, see `docs/design/architecture.md`.

Hand-maintained and unchecked. The tree below is a reader's map, not a
manifest: nothing requires a newly added file to appear here, and nothing
notices when one that is listed goes away.

---

## Dependency Direction

```
scripts/services/*                → lib/common.sh + lib/http.sh + lib/json.sh
scripts/services/{sonarr,radarr}  → lib/arr/  (additionally)
scripts/services/*                ↛ scripts/services/*  (no cross-service imports)
setup.sh                          → lib/common.sh + scripts/setup/*.sh
scripts/setup/*                   → lib/common.sh (via setup.sh sourcing)
scripts/setup/*                   ↛ scripts/setup/* (no cross-module imports)
tests/scenarios/*                 → tests/lib/* + tests/assertions/*
```

Two of these directions are machine-checked by `./tests/check.sh naming`
(`tests/naming.sh`): no service module may `source` another service's files,
and nothing under `scripts/setup/` may `source` a peer top-level
`scripts/setup/*.sh` module. Sourcing files inside the module's own directory
(`npm/main.sh` → `npm/certs.sh`, `hardening.sh` → `hardening/*.sh`) and the
orchestrator → stage seam (`wizard.sh`/`recovery.sh` → `stages/*.sh`) are the
sanctioned directions, not violations. Four top-level pairs predate the gate
and are exempted by name in its sanctioned-seam list; a seam listed there whose
import has gone fails as a stale entry:

```
scripts/setup/hardening.sh        → gpu.sh, storage.sh, fail2ban.sh   (uninstall dispatches to the module that owns each host artefact)
scripts/setup/env-gen.sh          → env-write.sh                       (a size split of env-gen.sh, not an independent module)
```

The gate resolves a `source` argument only when its directory variable is
derived from `${BASH_SOURCE[0]}` or `$SCRIPT_DIR`; an import assembled some
other way is invisible to it.

Cross-service logic that touches 2+ configurators goes in `scripts/flows/*.sh`
(loaded by configure.sh; empty today).

## Adding a New Service

1. Add container to `docker-compose.yml` (image, ports, healthcheck, volumes, profile). Pick a free host octet from the `mediastack` IP map in the network-block comment and express it as `${MEDIASTACK_NETWORK_PREFIX}.X` — every bridge service is pinned, no auto-allocation. `network_mode: host` services skip this.
2. Create `scripts/services/<svc>/main.sh` with `configure_<svc>()` function
3. Add `<svc>` to the loop in `scripts/configure.sh` (ordering matters — after dependencies)
4. Add config.yml section if the service needs user-editable parameters
5. Extract `templates/*.json` only for static payloads (no variable substitution) with 4+ fields
6. Put non-trivial pure JSON/policy transforms in `scripts/services/<svc>/render/*.py` when shell would only be a wrapper
7. Update this file's tree

## Bumping a Service Version

Image tags live in `docker-compose.yml` (the source of truth); `docs/operations/upgrades.md` records each
service's pin policy and preflight command. To bump a service safely:

1. Pick the candidate tag. Read the service's row in `docs/operations/upgrades.md` (pin policy + touchpoint).
2. Preflight it **without editing compose** — patch the DinD copy and run the service's oracle:
   `MS_TEST_IMAGE_OVERRIDES="<svc>=<candidate-ref>" ./tests/run.sh <preflight-scenario>`
   (most services use `fresh-install`; wireguard → `wireguard`, npm → `npm-heal`, fail2ban →
   `fail2ban-drift`, ddns-updater → `ddns-seed`; always read the service's row for the exact token).
3. If the API/env/config shape changed, update the touchpoint files (service `main.sh`, and where
   relevant `scripts/setup/env-gen.sh`, `stages/stage2.sh`, `scripts/lib/`, pre-seeded `config/`)
   and explain the rationale in the PR when the change is behavioral.
4. Edit the tag in `docker-compose.yml`. If the pin **level** changed (e.g. `:latest` → exact patch),
   update the service's `docs/operations/upgrades.md` pin-policy token and the matching image-pin policy note.
5. Re-run the preflight scenario + `./tests/run.sh smoke`; run `./tests/unit/upgrades-manifest.sh`.
6. If the scheduled image-drift workflow alerted, refresh `docs/operations/image-digests.lock` only after the local DinD preflight passes. Stable-channel installs pin runtime image refs to this lock through `docker-compose.override.yml`.
7. Major / API-unstable bumps are a clean cutover, not an in-place upgrade: `docker compose down -v && ./setup.sh --full`.

Preflight checks API **shape** only (via the service's scenario/assertions oracle); it does not catch
config-time breaks. For a major bump, run the service's own battery plus `fresh-install` where
relevant — `fresh-install` does **not** start the `remote` (wireguard) or `subtitles` (bazarr)
profiles, so those need their own scenarios (wireguard: `smoke` + `wireguard` + the access-tier
scenarios).

## Evolution Triggers

- Service main.sh > 200 lines → extract helpers within the service dir
- Feature touches 2+ services → `scripts/flows/*.sh`, not inline in a service
- New shared Sonarr/Radarr pattern → `scripts/lib/arr/`
- New DDNS provider → registry cells in `scripts/lib/ddns-providers.sh` (`_DDNS_*` parallel arrays) + a field validator in `scripts/lib/validators.sh` + a `tests/unit/ddns-config.sh` fixture + docs. No wizard/day-2 flow-code edits — that is the whole point of the shared registry.
- New test scenario → `tests/scenarios/<name>.sh` + register in run.sh case statement
- Pre-seeded config for a new service → add the template under `config/examples/defaults/<svc>/…` (tracked) and gitignore the live `config/<svc>/` copy; `seed_config_from_templates` copies it on install automatically
