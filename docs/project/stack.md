# Stack

Tech-stack contract for MediaStack. Source of truth for languages, runtime,
services, commands, and tooling decisions. Consumed by `docs/project/structure.md` and the
project documentation. Hand-maintained and unchecked: the service table, the
container count and the DDNS provider list are read from the tree by hand, so
re-read them when a service changes.

---

## Project Profile
- Type: Self-hosted Docker Compose deployment tool + bash configuration engine
- Scale: Production (single-box, designed for non-technical end users)
- Deployment: Bare Debian 11/12/13 (headless), single machine; 13 (Trixie) is the newest verified
- Budget: Hobby / self-hosted (no cloud costs)
- Team: Solo-maintained project

## Language & Runtime
- Primary: Bash 5.x (Debian default)
- Secondary: Python 3.9+ (small render/config helpers using the stdlib plus distro `python3-yaml`; no pip)
- Runtime: Debian 11 (Bullseye), 12 (Bookworm), or 13 (Trixie), headless. 11 is the floor (Python 3.9+, bash 5.x); 13 is the newest verified on real hardware
- Package manager: apt (system packages only; no pip/npm/cargo)
- Shell: bash with `set -euo pipefail` throughout

## Infrastructure
- Container engine: Docker Engine, installed by `setup.sh --full` from Docker's own apt repo. `scripts/setup/checks.sh` requires the daemon to be present and reachable; it does not enforce a minimum version.
- Orchestration: Docker Compose v2 plugin — `docker compose` (space), not the standalone `docker-compose`. `checks.sh` requires the plugin form.
- Images: 19 third-party containers (see Services table)
- Network: Single Docker bridge network with static service IPs; setup selects a non-overlapping `/24` inside `172.16.0.0/12` and writes it to `.env`
- Config format: YAML (config.yml) + .env (generated by setup.sh)
- Config application: Bash scripts call service HTTP APIs (curl + jq)

## Test
- Framework: Custom bash E2E harness (Docker-in-Docker)
- Scenarios: smoke (~90s), fresh-install (~15-18 min warm), focused staged-setup scenarios
- Unit tests: every `tests/unit/*.sh`, discovered by glob
- DinD base: Debian-based (not Alpine) — matches production distro
- Image cache: Pull-through registry mirror + host sideload (dodges Hub rate limit)
- Commands:
  - Smoke: `./tests/run.sh smoke`
  - Full: `./tests/run.sh fresh-install`
  - Staged setup/recovery: pass the scenario names to `./tests/run.sh`; `tests/README.md` documents each
  - Real public WAN/DNS/DDNS/LE proof: operator-run `tests/gcp-vm/` harness
  - Real Debian/GPU/UFW/systemd proof: operator-run `tests/lan-host/` harness
  - Keep DinD after a failed run: `./tests/run.sh smoke --keep`
  - Cold cache: `./tests/run.sh --no-cache smoke`
  - Candidate-image preflight: `MS_TEST_IMAGE_OVERRIDES="wireguard=ghcr.io/wg-easy/wg-easy:16.0.0" ./tests/run.sh wireguard` — test a new image tag in the DinD compose copy before editing compose (see `docs/operations/upgrades.md`)
  - Manifest guard: `./tests/unit/upgrades-manifest.sh` — keeps `docs/operations/upgrades.md` in sync with compose tags
  - CI image drift alert: scheduled GitHub workflow resolves remote image digests and compares them with `docs/operations/image-digests.lock`; Stable-channel installs pin runtime images to that record, so run the matching local DinD preflight before updating it.
  - Cleanup leaked volumes: `docker volume prune -f`

## Lint / Format / Type Checking
- CI runs shell syntax checks, Python bytecode checks, compose rendering, focused unit tests, the upgrades manifest guard, public secret/private-file guards, and wizard PTY scenarios.
- Every tracked shell file is shellcheck- and shfmt-clean; both are gated in CI (`lint-shellcheck`, `format-shfmt`) and reproducible locally via `./tests/check.sh lint` / `./tests/check.sh shfmt` (pins in `tools.toml`).
- Python helpers use the stdlib plus distro PyYAML and are ruff- and mypy-checked in CI (`lint-ruff`, `type-mypy`); run locally with `./tests/check.sh ruff` / `./tests/check.sh mypy`.

## CI/CD
- GitHub Actions runs focused validation plus the scheduled image-drift alert.
- Local DinD scenarios remain the primary integration proof surface.

## Hosting
- Platform: Self-hosted bare metal (user's own Debian box)
- Remote access: NPM reverse proxy + Let's Encrypt + WireGuard VPN
- DDNS: Optional curated 6-provider wizard picker (Dynu, DuckDNS, deSEC, dynv6, Cloudflare, Porkbun) rendering `config/ddns-updater/config.json`; ddns-updater itself supports many more upstream. Credential handling: see `docs/setup/configuration-schema.md`
- Cost: $0/mo (hardware owned by user)

## Host Dependencies (installed by setup.sh --full)

The authoritative list is the `apt-get install` line in `scripts/setup/packages.sh`
plus the on-demand installs around it. The notes below cover the packages worth
explaining and are not checked for completeness by anything.

- docker-ce, docker-compose-plugin
- python3, python3-yaml (config.yml parsing)
- curl (API calls + healthchecks + the wizard's primary connection speed test via Cloudflare)
- envsubst (gettext-base — legacy shell-template compatibility; variable JSON uses Python/json_body)
- openssl (password/hash generation)
- git (nvidia-patch reviewed commit fetch/checkout)
- htop (interactive process/CPU/memory monitor)
- bind9-dnsutils (dig — DNS troubleshooting for remote access/DDNS/VPN)
- smartmontools (smartctl — disk health monitoring)
- inotify-tools (inotifywait — the fail2ban log-rotation reload watcher, `mediastack-fail2ban-reload.service`, watches for new date-stamped log files and reloads fail2ban so jail globs re-resolve; a `mediastack-fail2ban-reload-fallback.timer` also reloads every 6h as a floor if the watcher ever dies)
- ufw (firewall — default deny, allow service ports, LAN-only management)
- unattended-upgrades (automatic security-only patches)
- librespeed-cli (optional fallback for the wizard connection speed test; primary path is curl+Cloudflare)
- samba (optional SMB file share for LAN access)
- nfs-common (optional, installed only when managed NAS/NFS storage is selected)
- Optional: nvidia-driver + nvidia-container-toolkit, or vaapi drivers (GPU transcoding)

## Commands Quick Reference
```bash
# Interactive launcher (front-door for non-technical users)
./mediastack

# First-time setup (bare Debian)
./setup.sh --full

# First-time setup (Docker already installed)
./setup.sh

# Retry or verify remote HTTPS/WireGuard after Stage 1
./setup.sh --remote

# Retry hardware transcoding after skipped/fixed/new GPU
./setup.sh --transcoding

# Guarded NVIDIA Unlock maintenance (normally launched from ./mediastack)
./setup.sh --nvidia-unlock-update
./setup.sh --nvidia-unlock-repatch

# Re-configure after editing config.yml
./scripts/configure.sh

# Update service images for the selected IMAGE_CHANNEL (does not prune host images by default)
./scripts/update.sh

# Optional: also prune dangling images host-wide after the update
./scripts/update.sh --prune

# Day-2 health & security: ./mediastack → "Health & security" → "Run all checks" (fail2ban regex-drift/jails, TLS expiry, DNS drift, disk %, UFW, DOCKER-USER chain)
# Day-2 per-service updates: ./mediastack → "Manage updates" (status, per-service updates)
# Day-2 change quality profile: ./mediastack → "Features & settings" → "Change quality profile" (resolution × size, renamed in place, no orphan)
# Day-2 uninstall: ./mediastack → "Uninstall MediaStack" (transactional teardown; removes only recorded MediaStack host changes; data/ and config/ preserved)
# Per-service update-availability scan (table / TSV):
python3 scripts/image_drift.py --status
python3 scripts/image_drift.py --status-tsv

# README Stable-baseline badge guard (no network; derives from docs/operations/image-digests.lock):
python3 scripts/image_drift.py --check-readme-badges README.md

# Re-apply NVIDIA patch after driver update
./scripts/nvidia-repatch.sh

# Run tests
./tests/run.sh smoke
./tests/run.sh fresh-install
./tests/run.sh <scenario> [<scenario> ...]   # names: tests/scenarios/

# Validate compose changes
cp .env.example .env && docker compose config --quiet && docker compose --profile proxy config --quiet && docker compose --profile remote config --quiet && docker compose --profile autoheal config --quiet && rm .env

# Service operations
docker compose up -d                         # Core stack (includes Beszel)
docker compose --profile proxy up -d         # + NPM, fail2ban, DDNS (auto when DOMAIN set)
docker compose --profile remote up -d        # + WireGuard
docker compose --profile subtitles up -d     # + Bazarr
docker compose --profile autoheal up -d      # + unhealthy-container restarter
docker compose down
docker compose logs -f <service>
```

## Decision Log
- Container images: linuxserver for *arr apps (consistent PUID/PGID), official for Jellyfin (better maintained), hotio for Unpackerr (only maintained image).
- Reverse proxy: NPM over raw nginx — target users won't edit nginx configs; NPM has web UI + built-in Let's Encrypt.
- VPN: wg-easy over linuxserver/wireguard — web UI for peer management, no manual conf editing.
- DinD test base: Debian over Alpine — BusyBox grep lacks -P, envsubst missing from Alpine default, musl/glibc edge cases. Matches production distro.
- CI covers syntax, compose rendering, focused unit checks, public guards, wizard PTY scenarios, and image-digest drift alerts against the committed tested record. Full image-backed integration proof remains local/manual DinD so GitHub Actions does not need privileged nested Docker pulls.
- Python uses the stdlib plus distro `python3-yaml`: small render/config helpers, no pip dependencies or venv. Keeps the host dependency footprint minimal.
- Config via APIs: Services are configured by calling their HTTP APIs from bash, not by templating config files. More robust across image version upgrades.

## Reconsider If
- Adding a non-bash component (Go CLI, web UI) — would need a build step and proper CI.
- Supporting non-Debian distros — would need to abstract package management.
- Multi-box deployment — would outgrow single Docker Compose; consider Ansible or similar.
- Team grows past solo — should add shellcheck + shfmt + CI pipeline.
