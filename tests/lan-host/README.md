# Real-Host Testing (LAN / Bare-Metal)

End-to-end testing on a real Debian host via SSH. Complements the DinD test suite (`docs/testing/README.md`) by catching issues that only manifest on real hardware: GPU passthrough, UFW interaction, systemd services, disk I/O timing, and container image behaviour differences between DinD's nested Docker and a bare-metal Docker daemon.

## At a glance

Two ways to drive a real-host run, depending on what you're validating:

| Mode | Command | Validates | Needs |
|---|---|---|---|
| **A — LAN baseline** (non-interactive) | `DEMO=1 ./setup.sh --full` | install, GPU, UFW, systemd, disk I/O on bare metal — `example.com` defaults, no public access | nothing extra |
| **B — full remote-access** (interactive) | `./setup.sh --full`, answer the prompts | everything in A **plus** your real domain, DDNS push, and Let's Encrypt TLS | a domain + Dynu creds (the same values as `tests/.env.gcp`) |

**Which do I use?** Mode A is the common case — the bare-metal counterpart to the DinD suite, catching hardware/OS issues DinD can't. Reach for Mode B (or the GCP suite) only when you specifically want to exercise real DNS/TLS/DDNS. The GCP suite *automates* Mode B in the cloud; on real hardware you answer the wizard yourself, so there's no creds file to manage.

The rest of this doc is the full workflow — SSH setup → rsync → wipe → run → probe. Jump to [Running the Installer](#running-the-installer) for the two modes in detail.

## Prerequisites

- A Debian 12/13 host with SSH access and `sudo` (the "target")
- Your dev machine has the MediaStack repo checked out (the "source")
- `rsync` and `ssh` on both machines

## SSH Key Setup

Generate a key (skip if you already have one):

```bash
ssh-keygen -t ed25519 -C "mediastack-dev"
```

Copy it to the target:

```bash
ssh-copy-id user@<target-ip>
```

Verify passwordless login:

```bash
ssh user@<target-ip> "hostname"
```

If the target has UFW enabled, ensure SSH is allowed (not rate-limited):

```bash
# On the target:
sudo ufw allow 22/tcp
```

## Rsync the Codebase

Push local code to the target, excluding runtime state:

```bash
rsync -az --delete \
  --exclude='.env' \
  --exclude='config/' \
  --exclude='docker-compose.override.yml' \
  /path/to/MediaStack/ user@<target-ip>:/home/user/MediaStack/
```

- `--delete` removes files on the target that no longer exist locally
- `.env`, `config/`, and `docker-compose.override.yml` are excluded because they're generated by `setup.sh` — syncing them would inject stale state from your dev machine
- Run this before every test to ensure the target has your latest changes

## Clean Wipe (Full Reset)

Stop all containers, remove their state, and delete generated files:

```bash
# Stop all compose services (catches profiled services like npm, fail2ban, bazarr)
ssh user@<target-ip> 'cd ~/MediaStack && docker compose --profile all down 2>/dev/null'

# Catch any stragglers not managed by compose
ssh user@<target-ip> 'docker stop $(docker ps -q) 2>/dev/null; docker rm $(docker ps -aq) 2>/dev/null'

# Remove Docker volumes (database state, download history)
ssh user@<target-ip> 'docker volume prune -f'

# Remove config dirs (may be root-owned from container mounts), .env, and override
ssh user@<target-ip> 'sudo rm -rf ~/MediaStack/config ~/MediaStack/.env ~/MediaStack/docker-compose.override.yml'
```

Important: stop containers **before** deleting config. Running containers recreate their config files (e.g. Jellyseerr's `settings.json`) immediately after deletion, which causes stale state on the next install.

To remove NVIDIA drivers (for retesting GPU detection from scratch):

```bash
# Check what's installed
ssh user@<target-ip> 'dpkg -l | grep -i nvidia; ls /usr/src/nvidia* 2>/dev/null; command -v nvidia-smi && nvidia-smi --query-gpu=driver_version --format=csv,noheader 2>/dev/null'

# Remove .run-installed driver (DKMS module + leftover files)
# Note: don't rm /usr/bin/nvidia-* — that deletes nvidia-container-runtime too
ssh user@<target-ip> 'sudo dkms remove nvidia/<version> --all 2>/dev/null; sudo rm -rf /usr/src/nvidia-*; sudo rm -f /usr/lib/x86_64-linux-gnu/libnvidia* /usr/lib/x86_64-linux-gnu/libcuda* /usr/bin/nvidia-smi /usr/bin/nvidia-debugdump /usr/bin/nvidia-persistenced /usr/bin/nvidia-cuda-mps-control /usr/bin/nvidia-cuda-mps-server'

# Remove debian-packaged driver (if installed via apt)
ssh user@<target-ip> 'sudo apt-get purge -y firmware-nvidia-graphics nvidia-driver 2>/dev/null; sudo apt-get autoremove -y'

# Restore nouveau (the .run installer blacklists it)
ssh user@<target-ip> 'sudo rm -f /etc/modprobe.d/blacklist-nouveau.conf; sudo update-initramfs -u'

# Clean up build artifacts
ssh user@<target-ip> 'sudo rm -rf ~/MediaStack/.nvidia-tmp ~/MediaStack/.nvidia-patch'
```

The nvidia-container-toolkit packages can be left in place — they're just the Docker runtime integration and setup.sh will skip reinstalling them.

To also wipe media data (rarely needed):

```bash
ssh user@<target-ip> 'sudo rm -rf /data'
```

## Running the Installer

Pick the mode that matches what you want to validate (see [At a glance](#at-a-glance)).

### Mode A — LAN baseline (non-interactive)

The common case: bare-metal install, GPU passthrough, UFW, systemd, disk I/O — using `example.com` defaults, so no public-access path is attempted.

```bash
ssh user@<target-ip> "DEMO=1 bash /home/user/MediaStack/setup.sh --full"
```

- `DEMO=1` — bypasses the interactive wizard and writes `.env` / `config.yml` from generated defaults (`DOMAIN=example.com`, so the remote/DDNS/TLS path is skipped)
- `--full` — includes OS packages, Docker install, GPU detection, hardening
- Use the absolute path to `setup.sh` since SSH starts in `$HOME`, not the repo dir

### Mode B — full remote-access (interactive)

The bare-metal counterpart to the GCP suite: exercises your real domain, Dynu DDNS push, and Let's Encrypt TLS on actual hardware. Run **without** `DEMO=1`, over a TTY, and answer the Stage 2 prompts:

```bash
ssh -t user@<target-ip> "cd /home/user/MediaStack && ./setup.sh --full"
```

The wizard collects these (the same values you put in `tests/.env.gcp`):

| Prompt | Enter |
|---|---|
| `Your hostname (e.g. yourname.mywire.org)` | your real domain |
| `Use Dynu DDNS? [y/N]` | `y` |
| `Dynu username` | your Dynu username |
| `Dynu password` | your Dynu password |

- `ssh -t` allocates a TTY so the interactive prompts work over SSH.
- **Let's Encrypt staging for repeat loops:** `NPM_LE_SERVER` is read from the environment / `.env` (it is *not* a wizard prompt). Pre-set it to the staging endpoint to dodge rate limits while iterating; leave it unset for a final trusted-cert run:
  ```bash
  ssh -t user@<target-ip> "cd /home/user/MediaStack && NPM_LE_SERVER=https://acme-staging-v02.api.letsencrypt.org/directory ./setup.sh --full"
  ```
- **Why there's no non-interactive remote mode:** the DDNS preflight can't be navigated by `DEMO=1` — which is exactly why the GCP runner scripts the wizard. On real hardware you just answer the prompts yourself.

`UI_DEMO=1` still exists for UI simulation and screenshot-style flows, but it is not the recommended installer path.

## Running Just configure.sh

If containers are already running and you only want to re-test the configuration step:

```bash
# Rsync first to push code changes
rsync -az --delete --exclude='.env' --exclude='config/' --exclude='docker-compose.override.yml' \
  /path/to/MediaStack/ user@<target-ip>:/home/user/MediaStack/

# Run configure.sh (uses existing .env and running containers)
ssh user@<target-ip> "bash /home/user/MediaStack/scripts/configure.sh"
```

## Probing Services

After a run, verify each service is configured correctly:

```bash
# Get API keys from the target's .env
ssh user@<target-ip> "grep '_API_KEY=' /home/user/MediaStack/.env"

# Check a specific service (example: Sonarr download clients)
ssh user@<target-ip> 'curl -sf http://localhost:8989/api/v3/downloadclient \
  -H "X-Api-Key: <sonarr-key>" | python3 -m json.tool'

# Check all container health
ssh user@<target-ip> 'docker ps --format "table {{.Names}}\t{{.Status}}"'

# Check qBittorrent preferences (login required)
ssh user@<target-ip> 'source /home/user/MediaStack/.env; \
  RESP=$(curl -sf -c /tmp/qbt.jar http://localhost:8080/api/v2/auth/login \
    --data-urlencode "username=$JELLYFIN_ADMIN_USER" \
    --data-urlencode "password=$JELLYFIN_ADMIN_PASSWORD"); \
  echo "Login: $RESP"; \
  curl -sf -b /tmp/qbt.jar http://localhost:8080/api/v2/app/preferences | python3 -m json.tool'
```

## NVIDIA Healthcheck + Autoheal Probe

On an NVIDIA-configured host, this verifies the Jellyfin healthcheck catches
container-local NVIDIA failures and that autoheal recovers by stop/starting the
container. It does not break the host driver.

```bash
ssh user@<target-ip> 'cd ~/MediaStack && set -euo pipefail
before_pid=$(docker inspect jellyfin --format "{{.State.Pid}}")
docker exec jellyfin sh -c "cat > /usr/local/bin/nvidia-smi <<'"'"'WRAP'"'"'
#!/bin/sh
if [ -f /tmp/force-nvidia-smi-fail ]; then
  echo simulated stale NVIDIA runtime >&2
  exit 255
fi
exec /usr/bin/nvidia-smi \"$@\"
WRAP
chmod +x /usr/local/bin/nvidia-smi
touch /tmp/force-nvidia-smi-fail"

removed=0
for i in $(seq 1 72); do
  health=$(docker inspect jellyfin --format "{{.State.Health.Status}}")
  pid=$(docker inspect jellyfin --format "{{.State.Pid}}")
  echo "t=$((i*10))s health=$health pid=$pid"
  if [ "$pid" != "$before_pid" ] && [ "$removed" = 0 ]; then
    docker exec jellyfin rm -f /tmp/force-nvidia-smi-fail
    removed=1
  fi
  if [ "$removed" = 1 ] && [ "$health" = healthy ]; then
    docker exec jellyfin sh -c "rm -f /usr/local/bin/nvidia-smi /tmp/force-nvidia-smi-fail"
    docker exec jellyfin nvidia-smi >/dev/null
    echo "recovered"
    exit 0
  fi
  sleep 10
done
docker exec jellyfin sh -c "rm -f /usr/local/bin/nvidia-smi /tmp/force-nvidia-smi-fail" 2>/dev/null || true
exit 1'
```

Expected sequence: `healthy` → `unhealthy` → PID changes (autoheal stop/start)
→ `healthy`, and the final `docker exec jellyfin nvidia-smi` succeeds. Docker's
`RestartCount` does not necessarily change for autoheal's manual stop/start, so
track PID or `StartedAt` instead.

## Common Gotchas

**qBittorrent v5.x login returns HTTP 200 for failures.** The body is `"Ok."` on success and `"Fails."` on failure — always check the body, not the status code.

**qBittorrent IP bans after failed logins.** Too many failed attempts triggers a temporary ban. Restart the container to clear it: `docker restart qbittorrent`.

**`docker compose` needs the compose file.** Commands like `docker compose down` fail with "no configuration file" if run outside the repo directory or if `.env` is missing. Use `docker stop/rm` directly when the compose context is broken.

**Config dirs may be root-owned.** Container mounts create dirs as root. Use `sudo rm -rf` when cleaning.

**Cloudflare-protected indexers fail without FlareSolverr.** 1337x, eztv, kickasstorrents-to, and extratorrent-st are behind Cloudflare. Jackett returns error 900 and the indexer add fails. This is expected in default configuration.

## Iterating Quickly

The typical dev loop:

1. Edit code locally
2. `rsync` to target
3. `ssh ... "bash /home/user/MediaStack/scripts/configure.sh"` (if only configure.sh changed)
4. Probe the affected service to verify

For changes to `setup.sh`, `docker-compose.yml`, or `.env` generation, a full wipe + reinstall is needed. For changes to service configurators only, re-running `configure.sh` against existing containers is usually sufficient.
